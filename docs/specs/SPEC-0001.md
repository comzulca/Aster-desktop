# SPEC-0001 — Aster-desktop v0.1.0 MVP

Status: design baseline for implementation; acceptance evidence pending. Owner: Aster-desktop engineering. Created 2026-09-24 UTC. Stability: IDs never recycled; changes to normative behavior require this spec, corresponding threat/ADR, test and evidence to change together.

## Product outcome and release boundary

Build a Windows 11 local-first desktop harness with the user's original Aster visual reference, a closed two-model NVIDIA catalog, host-held credentials, bounded project reading and model-assisted file proposals. The model cannot commit, run code, browse the web, install dependencies or grant itself access. A human explicitly confirms **each** file operation. The default model is `nvidia/nemotron-3.5-lightning-30b-a3b`; `meta/muse-glimmer-30b` is the second model. Both are intended to stream, with separate provider fixtures and live verification. The Linux workspace is a development area, not the user's requested Windows checkout or a production artifact.

`Deterministic` here means that fixed versioned policy plus identical validated input, host state and test fixture yield the same admission/denial, state transitions and terminal result. It does not mean identical LLM text, request timing, real provider availability or byte-identical installers.

### In-scope interaction

1. The user starts a session and chooses a model (Nemotron selected initially). The UI shows honest credential/network state.
2. The user enters their NVIDIA key only via native trusted Windows entry. The Rust host reads the Windows user credential and sends HTTPS requests to the fixed NVIDIA origin. No secret bytes enter WebView state, logs, project files or CI.
3. The user sends a message, views streamed reply text, and can cancel. Reasoning fields are separately classified and not silently merged into ordinary answer content.
4. The user selects one local project root using a trusted native dialog. The host issues bounded grants for allowed UTF-8 text reads. Before sending any selected file excerpt to NVIDIA, the user explicitly chooses what content to disclose in that request.
5. A model-produced edit suggestion is parsed into a bounded typed diff proposal. A **native host-owned review window** displays the complete exact target and change. The host alone binds it to one request, root, path/file identity, old/new SHA-256, nonce, expiry and use count=1. The user approves the **specific operation and diff** in that trusted window; a WebView `approved=true` is never sufficient. The host revalidates immediately before publication. Existing-file replacements are proposal-only until their Windows-specific native conflict/recovery gate passes. Creating a new file also requires its own native gate.

### Data and trust assumptions

Messages and responses may leave the device only as an explicit NVIDIA request. Project content never leaves implicitly. Conversation state is ephemeral in v0.1.0; no persistent chat history, attachment store, telemetry, analytics or export. File mutation intent/recovery journal, if introduced, is security-critical local persistence requiring separate schema, bounds and crash tests. Windows Credential Manager generic credentials are accessible to the same Windows account; no claim of isolation against another process running as that user.

### Non-goals

Arbitrary provider endpoints, model-controlled function calling, shell, code execution, web/browser/MCP, background autonomy, recursive workspace upload, modifying files outside the selected root, storing chat history, multiuser authorization, app self-update, signed production installer and hard billing caps. An unavailable feature must be visibly unavailable, not an enabled placeholder.

## Initial resource policy (version 1, provisional until implementation evidence)

Only one outstanding model request per conversation. One text file per read, UTF-8 only, maximum 1 MiB; no archives, binary files or recursive upload. At most one pending typed proposal per conversation across existing-file and new-file operations, with at most 256 KiB changed content; preparation of another operation revokes the prior candidate. The internal host proof seam has a combined ceiling of four pending candidates across conversations, not four per operation type. Native review is an explicit host-owned action, not a model/tool loop. All shipping proposal/apply flags remain disabled pending independent activation evidence. Stream response maximum 8 MiB, one SSE frame maximum 256 KiB and 262,144 events maximum; connect deadline 10 seconds, first headers 30 seconds, idle between frames 60 seconds and total request deadline 900 seconds. No implicit retry and no model tool-call loop. Any adjustment is a versioned policy and test change, not an undocumented UI setting. NVIDIA `max_tokens` is provider-specific and must not be confused with local byte limits.

## Acceptance decision

### Preserve-existing-credential diagnostic (2026-09-30 UTC)

The owner confirms that a real NVIDIA credential already exists and must be preserved. ADR-0005 defines a separate synthetic GUI acceptance route; normal configure/change/delete controls must not be used to obtain destructive synthetic evidence. The diagnostic takes no target/key/URL/path override, uses native UI only, accepts only the known non-secret fixture password, and exits before normal Host/Tauri/provider initialization. Any raw existing entry blocks creation, even when its representation is invalid. No automatic cleanup occurs on cancellation, error, interruption or panic. Manual GUI evidence remains NOT RUN until the exact new artifact is tested. Shared primitive evidence is not proof of the full production Tauri deletion handler. This change grants no new shipping IPC or workspace capability and does not spend either live canary.

### Engineering candidate clarification (2026-09-30 UTC)

ADR-0004 records the owner's unsigned engineering-only release choice, existing administrator-account manual acceptance (no guest/new account), manual Windows Credential Manager key entry, and authorization for exactly two minimal live NVIDIA requests, one per model. These are authorizations, not PASS results. New proof procedures T-028–T-032 cover credential representation, strict proposal parsing, lossless native review, new-file journal/no-clobber fixtures and grant invalidation. Workspace disclosure and both apply capabilities remain independently gated; a fixture result must not activate them or claim Windows 11 acceptance.

The source/demo can be promoted only as far as proven. The user-requested existing-file apply feature remains **conditional, NOT RUN** until a sound Windows publication design and native race/recovery evidence exist; an unverified implementation must display proposal-only. Do not claim a signed installer, Windows credential integration, live NVIDIA acceptance or private GitHub permissions from a Linux fixture run.
