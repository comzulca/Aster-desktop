## Product outcome and release boundary

Build a Windows 11 local-first desktop harness with the user's original Aster visual reference, a closed two-model NVIDIA catalog, host-held credentials, bounded project reading and model-assisted file proposals. The model cannot commit, run code, browse the web, install dependencies or grant itself access. A human explicitly confirms **each** disclosure or file operation. The default model is `nvidia/nemotron-3.5-lightning-30b-a3b`; `meta/muse-glimmer-30b` is the second model. Both are intended to stream, with separate provider fixtures and live verification. A development worktree or hosted runner is not the installed Windows 11 laptop artifact.

`Deterministic` here means that fixed versioned policy plus identical validated input, host state and test fixture yield the same admission/denial, state transitions and terminal result. It does not mean identical LLM text, request timing, real provider availability or byte-identical installers.

### In-scope interaction

1. The user starts a session and chooses a model (Nemotron selected initially). The UI shows honest credential/network state.
2. The user enters their NVIDIA key only via native trusted Windows entry. The Rust host reads the Windows user credential and sends HTTPS requests to the fixed NVIDIA origin. No secret bytes enter WebView state, logs, project files or CI.
3. The user sends a message, views streamed reply text, and can cancel. Reasoning fields are separately classified and not silently merged into ordinary answer content.
4. The user selects one local project root using a trusted native dialog. Protocol 2 may expose four Boolean capability facts: `projectRead`, `proposals`, `applyNewFile`, and `applyExistingFile`. The host is authoritative; `applyExistingFile` is hard false in v0.1.0. Native file selection returns only a bounded relative path, request ID, SHA-256 and byte count to the renderer. Project plaintext remains in the host.
5. Before a selected project file is sent to NVIDIA, the host constructs the exact serialized provider body, displays that complete body in a native review window owned by the authenticated main application HWND, consumes one non-serializable approval, revalidates the root/file/hash, and transmits those exact bytes once. A project-bearing prompt and its derived answer use an ephemeral reservation and are excluded from later conversation continuation.
6. A model-produced edit suggestion is parsed into one bounded typed proposal. A **native host-owned review window** displays the complete exact target and change. The host alone binds it to one request, root, path/file identity, old/new SHA-256, nonce, expiry and use count=1. The user approves the **specific operation and diff** in that trusted window; a WebView `approved=true` is never sufficient. For a new file, the host revalidates immediately before publication, journals bounded metadata in a current-user DPAPI/private-DACL journal, uses `CREATE_NEW`, flushes and verifies the same handle, and recovers conservatively after interruption. Existing-file replacement stays proposal-only and `applyExistingFile=false` until a separate safe primitive and Windows race/crash/recovery proof exist.

### Data and trust assumptions

Messages and responses may leave the device only as an explicit NVIDIA request. Project content never leaves implicitly. Conversation state is ephemeral in v0.1.0; no persistent chat history, attachment store, telemetry, analytics or export. File mutation intent/recovery journal, if introduced, is security-critical local persistence requiring separate schema, bounds and crash tests. Windows Credential Manager generic credentials are accessible to the same Windows account; no claim of isolation against another process running as that user.

### Non-goals

Arbitrary provider endpoints, model-controlled function calling, shell, code execution, web/browser/MCP, background autonomy, recursive workspace upload, modifying files outside the selected root, storing chat history, multiuser authorization, app self-update, signed production installer and hard billing caps. An unavailable feature must be visibly unavailable, not an enabled placeholder.

## Resource policy (protocol 2 engineering candidate)

Only one provider request is active for the application at a time, and therefore at most one per conversation. Ordinary conversation input is host-bounded to 64 KiB, but the current renderer and composed project-bearing prompt use the narrower 32 KiB ceiling; oversize project content denies without truncation. Retained context is bounded to 512 KiB, 20 turns, 32 conversations and 64 request IDs per process session. One text file per read, UTF-8 only, maximum 1 MiB; no archives, binary files or recursive upload. Snapshot/proposal grants expire after five minutes and a host heartbeat runs every 60 seconds to remove expired plaintext and candidates. Failed/cancelled project egress revokes its snapshot; successful egress retains only the bounded one-use proposal right until expiry. At most one pending typed proposal per conversation across existing-file and new-file operations, with at most 256 KiB changed content; preparation of another operation revokes the prior candidate. The host has a combined ceiling of four pending candidates across conversations, not four per operation type. Native review is an explicit host-owned action, not a model/tool loop. Protocol 2 may report project read, proposal review and new-file apply as available on Windows engineering candidates; existing-file apply remains false. Stream wire response maximum is 8 MiB, accumulated answer maximum is 512 KiB, one SSE frame maximum is 256 KiB and 262,144 events maximum; connect deadline 10 seconds, first headers 30 seconds, idle between frames 60 seconds and total request deadline 900 seconds. No implicit retry and no model tool-call loop. Any adjustment is a versioned policy and test change, not an undocumented UI setting. NVIDIA `max_tokens` is provider-specific and must not be confused with local byte limits.

Manual GUI evidence remains NOT RUN until the exact new artifact is tested. Shared primitive evidence is not proof of the full production Tauri deletion handler. This change grants no new shipping IPC or workspace capability and does not spend either live canary.
