## Persistent conversations

FR-024 / SEC-021 / SEC-022: host-owned schema-1 saved conversations in a separate current-user DPAPI/protected-owner-DACL store. Maximum 128 saved conversations, 20 completed continuation turns and 512 KiB text per conversation; maximum 64 MiB domain payload and bounded record count. Refuse capacity exhaustion without silent truncation, deletion or overwrite. Titles derive locally from the first prompt; no automatic external title generation. Removal requires separate native confirmation and hides only that conversation through an encrypted tombstone, never deleting credentials, finances or file-recovery journals. No import/export or legacy model/history migration in this version.

Persist accepted intent before dispatch and a terminal transcript afterwards. Restarted incomplete requests become `interrupted` for display, not active/replayable requests. Restore no approvals, project rights or native state. Only complete eligible ordinary turns may become continuation, and every prior prompt/answer is re-admitted and reviewed in the full next outbound body. Incomplete/refused/truncated/unsafe answers cannot become automatic continuation. Switching/new-chat is disabled while the global request is active; Stop remains bound to that request. No renderer-authored transcript persistence, browser localStorage or chat content in the financial ledger. Initial removal uses a durable native-confirmed tombstone: the conversation disappears from visible history, but encrypted recovery records remain and disk quota is not freed. Do not label this permanent/secure erasure; separately reviewed checkpoint/compaction is required before physical reclamation.

## Request and resource contract

Credential compatibility clarification, 3 October 2026 (SEC-015 / AC-041 / T-051): the authentication guide illustrates `LLM|numeric-id|secret`, while a standalone owner-authorised catalogue diagnostic accepted an owner-provided opaque `LLM_` token. Support both closed native key representations without translating, trimming or repairing bytes. Retain the overall 8..256-byte ASCII bound; opaque tokens require `LLM_` plus at least 12 ASCII alphanumeric, underscore, hyphen or full-stop characters. Deny whitespace/control/non-ASCII bytes, unsupported prefixes and opaque punctuation outside that alphabet. Keep both formats host-only, with existing native confirmation/revocation and distinct Credential Manager custody; syntax never establishes billing or inference rights. The diagnostic adds no application GET route, file import, secret-export or paid-call permission. Add synthetic admission/decoder/header-boundary and secret-guard regressions before implementation, then rerun affected source checks. The catalogue observation is not T-059 canary acceptance.

Coupled data-admission clarification, 3 October 2026 (SEC-016 / AC-035 / T-045): case-insensitively deny both known Meta credential prefixes, `LLM|` and `LLM_`, in every newly submitted prompt and every prior user/assistant message selected for continuation. Neither allowed data classification nor native confirmation can override this denial. Use only non-secret synthetic fixtures in source; a source-scanner fixture exception is never a runtime admission exception. This bounded known-prefix control is not universal secret detection.

Source-guard clarification, 3 October 2026 (NFR-006 / AC-047 / T-057): recognise punctuation-bearing pipe-key text as well as the closed opaque alphabet; an exact non-secret fixture extended with `+`, `/` or `=` must not inherit a fixture exemption. Retain source-delimiter-aware, best-effort scanning and report no matching bytes. Synthetic positive and extension regressions precede the scanner change. This source check is neither native credential custody nor complete leak prevention.

Protocol and admission policy 3; independently version chat schema, budget schema, file journal and package manifest. Deny unknown IPC fields and incompatible host/renderer versions. Intent includes conversationId, requestId, exact fixed modelId, message, `dataClass` (`synthetic` or `public_eligible`) and reasoning effort (`minimal`, `low`, `medium`, `high`, `xhigh`; default medium). Unknown/prohibited classes, identifiers or models deny before network. Host builds one controlled developer instruction plus eligible visible history; no private reasoning, system/device identity, project path or key is appended.

Limits: user input 32 KiB UTF-8 in both UI and host; exact JSON body/context 512 KiB; 20 complete turns; 32 admitted conversation IDs and 64 request IDs per process; one active request globally; SSE frame 256 KiB, wire total 8 MiB, answer 512 KiB, 262144 events; connect 10s, headers 30s, frame inactivity 60s, total 900s; max completion 8192 including reasoning. Reject excess rather than silently summarising/truncating input.

Host sequence: reserve active slot -> admit all messages -> build immutable exact body -> native owner-window full-body/default-deny review -> durable budget reservation and pending transcript -> native Meta key -> durable dispatch intent -> transmit the approved allocation -> independent transcript/financial terminal handling. A failed post-dispatch request/cancel does not prove no charge. Only a transport preflight proving no send can release a possible-dispatch reservation automatically; uncertain network failures cannot. No serialisable renderer approval. No reconstruction after review. Cancelling and finishing produce exactly one request-bound terminal.

Provider serializer: HTTPS POST `https://api.meta.ai/v1/chat/completions`, Bearer key in host only, stream true, include_usage true, n=1, store=false, max_completion_tokens=8192, selected allowed reasoning effort. Omit sampling, tools and unsupported fields. Reject redirects/proxies/origin and route overrides. Validate chunk id/model/object/choice index and fixed identity, fragmented UTF-8/SSE, usage-only empty choices, refusal/tools, terminal framing and limits. `stop` requires valid closure; `length` is truncated, filters/refusals are refused; tools/functions denied. Usage is independent of the visible terminal status; missing/impossible/duplicate usage keeps money unresolved. HTTP errors map to local safe messages, never rendered provider bodies.

## Financial contract

FR-021/022 and SEC-018: £89 monthly application-admission ceiling, 90% warning, Europe/London calendar-month policy. Integers only (nanodollars/nanolibras; checked wider multiplication). Published fixture prices: 100/2/200 nanodollars per uncached/cached/completion token; reasoning is a subset of completion. Conservative request reserve: 106496000 nanodollars (1048576 input + 8192 completion, no cache). Prices are dated policy, not account billing proof.

No fabricated FX or tax. A separately confirmed configuration supplies opaque account ID, conservative GBP-per-USD rate in integer parts-per-million, margin/tax/payment-charge basis and validity interval (maximum 31 days). Missing/expired/invalid policy blocks dispatch. Configuration cannot raise £89, erase reservations or pretend to settle them. Reserve before dispatch, mark possible dispatch durably before network, settle only with consistent request/model-bound usage. Interruptions and ambiguous records retain reservation and require reconciliation. Monthly rollover never frees unresolved prior-period reservations. Detect backwards clock and implausible forward rollover; require explicit reviewed period reconciliation, not silent reset. Use one exclusive interprocess financial lease; preserve append-only flushed protected records with bounded integrity/schema validation. The store is not proof against rollback by a compromised same-user process or charges made outside Aster.

No financial-reset or arbitrary reconciliation/write primitive is exposed.
