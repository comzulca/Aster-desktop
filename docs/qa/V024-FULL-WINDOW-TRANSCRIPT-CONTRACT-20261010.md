## Resolved owner decisions versus proposed controls

The owner requires the full documented 1,048,576-token model window, not early compaction at the inherited 20-turn/512-KiB limit. Compaction may change active eligible model context only; it must preserve complete local display history, entry state/order and attachment provenance. A token window is not a proof of any maximum UTF-8, serialized JSON, encrypted-file, media or lifetime-history byte count. Do not invent a token-to-byte multiplier or silently use disk capacity as an early summary trigger.

The owner now chooses an initial **4 GiB (4,294,967,296 bytes)** for the **new encrypted display/context transcript history**, separately from processed attachments. There is no automatic trim, deletion, eviction or quota reclamation. At capacity, deny and warn about new writes; preserve the existing history and its readable data. This capacity choice is resolved, not a request for another owner choice about the initial number.

The proposed accounting metric is the aggregate **encoded ciphertext file length** across all new transcript domains: display/context chunks, index objects, manifests/control records and retained orphans, including objects from interrupted writes. All these objects share one 4-GiB aggregate ceiling; do not give each domain an independent 4-GiB allowance. Accounting is host-owned and must use actual bounded native object metadata, not renderer totals or a claimed counter in a manifest. Unknown, malformed or foreign objects fail health validation rather than become ignored bytes. The exact accounting, transaction reservation and native admission controls are still proposals requiring review and tests; there is no implemented 4-GiB store.

Logical ciphertext lengths do not equal physical disk allocation: filesystem clusters, directories, security metadata, other files and free-space races consume additional space. Legacy `history-v1`, existing `processed-media-v1`, finances, terms, profile, catalogue and credential proof remain separate and untouched; they can occupy additional space. No measured free-space headroom, physical allocation ceiling, sparse/compression behaviour, directory durability or power-loss guarantee is asserted here. Quota and available disk space are independent admission conditions; neither can waive corruption or identity checks.

Per-item 32-KiB composed prompt and 512-KiB answer limits remain unchanged until separately and explicitly reviewed. This draft does not remove active aggregate/turn/transport limits or claim that the current runtime can use the full window.

## Smallest proposed implementation seam

After root review only, a first slice may be a new private, initially unlinked pure layout/migration/replay core using synthetic memory fixtures, with at most `cfg(test)` linking after full source review. It has no `PrivateStore`, filesystem path, credential, provider, financial, native-review, renderer or IPC adapter. Supplied record lengths and hashes are fixture/trusted-host seams, not native accounting or authenticity proof. The exact module name and wire schema require approval before code.

Proposed closed concepts are opaque fixed record IDs/digests, `DisplayRevision`, `ContextRevision`, `LegacySourceProof`, `DisplayFragment`, bounded `IndexNode`, `ContextPlan` and `TranscriptCommit`. These are not permission-bearing types. All IDs, schemas, variants, versions, counts, order, duplicate detection and unknown-field denials need explicit limits; no arbitrary path, endpoint, command, unregistered model or external object reference belongs in them.

A proposed new fixed encrypted data domain holds inert fragments, index nodes and context plans. A separate new fixed encrypted commit/control domain holds the authoritative append-only chain. Names, domain envelope versions, per-object ciphertext ceilings, record-count ceilings and handle budgets remain unapproved design details. Both domains share the owner's single aggregate 4-GiB ceiling; legacy/domain version identifiers are not repurposed.

One authoritative `TranscriptCommit` binds the previous commit hash, exact display root and context root, both independent revisions, relevant source proof and a closed operation. Larger source inventories are hash-bound bounded index roots, not unbounded lists embedded in one commit. New data objects are inert until referenced by that final commit. There is no independent display/context activation and no mutable overwritten "current manifest". Missing commit means no new active version. Competing sequence successors, forks, duplicates, gaps, unexpected objects or inconsistent roots deny rather than select the highest filename or repair the chain.

## Lossless legacy projection and commit-last migration

1. Acquire a healthy, identity-pinned, side-effect-free snapshot of the fixed legacy history and relevant processed-media domain. Decode strict v1/v2 records without rewriting, recovery appends or field normalization. Preserve every original record/ciphertext in place.
2. Replay snapshots, durable removals and global eligibility invalidations in their original chained order. Select the latest valid visible conversation projections without resurrecting removed IDs or converting display text into continuation eligibility. Preserve original records as the historical source, not only a flattened export.
3. Bind `LegacySourceProof` to exact history domain/schema identity, complete sequence/tail hash, selected source record IDs/hashes/versions, removal/invalidation lineage, provider/model and exact media-domain sequence/tail and referenced-object proofs. A selected snapshot alone is insufficient to prove eligibility after a later Invalidate event.
4. Project every conversation ID/title/timestamp and ordered entry ID/role/content/request/state, every turn's pairing/class/eligibility, pending metadata and ordered attachment bindings losslessly. Cover all six current states: Completed, Failed, Cancelled, Truncated, Refused and Interrupted. Preserve empty/optional-field distinctions admitted by each legacy schema; reject v1 attachment-field injection rather than upgrade hostile data.
5. Preserve pending source data as source history. An explicit target recovery event/projection may mark interrupted runtime display without recreating an active request. If that recovery event needs durable bytes, include it in migration admission before committing; no write-at-capacity exception is presumed. Read-only restored pending presentation must never pretend an unappended state transition is durable or block local viewing merely to recreate a worker.
6. Prepare bounded chunks/index/context objects, admit the full proposed transaction under reviewed quota/identity rules, append them immutably and verify exact readback. Revalidate unchanged legacy source proof immediately before the authoritative commit. A changed source invalidates the proposal; no automatic merge, retry or source rewrite follows.
7. Append and verify the single authoritative cross-domain commit **last**. Only complete checked replay may activate the new display/context roots. This is a proposed publication protocol, not a claim that the existing store provides multi-domain atomicity or power-failure durability.

No archive, migration or source proof restores current-key proof as admission, active requests, account/device sessions, original allocations, tool/disclosure/native approvals, counts as permits, replay rights, financial reservations or unknown-spend resolution. Financial records remain independently authoritative and unchanged. Rollback/failure handling never re-enables an obsolete eligible context or resends a provider request. A still-readable legacy view is local data only; it cannot become a silent fallback sending path when the new target is unhealthy.

## Independent revisions, eligibility and original exclusions

`DisplayRevision` changes when display entries, status, title, removal or explicit recovery presentation change. `ContextRevision` changes when the admitted eligible context source set, pairing/class/provenance, invalidation or active summary changes. A failed/pending/status-only display append need not add context; a summary may change context without rewriting a single historical display entry. One commit binds both roots/revisions and makes those relationships explicit. Every digest covers ordered source identities and exact materialized bytes, not just token totals.

Future candidates bind the **pre-append** context identity and their own exact bytes/settings. Full-window capacity must be checked before appending that candidate into context. Display persistence of admitted pending intent, dispatch and terminal publication need their own reviewed transaction ordering and independent finances; this draft does not authorise orchestration. Counts and native approvals remain ephemeral, cancellation/deadline/process/current-key-generation bound and single-use where applicable. A new revision invalidates stale counts/review material.

A summary references exactly the eligible prefix and source hashes it covers, remains lower-trust inert data, and never becomes a replacement transcript, tool instruction or permission. Eligible source material alone does not prove eligible summary output. Re-admit exact generated summary bytes, class and every later disclosure through Contributor content/secret/privacy gates. Malformed, refused, truncated, stopped, stale or ineligible summaries cannot replace active context. Preserve recent turns and strict pairing; do not silently omit documents or treat a summary as future preventive-headroom proof.

Personalization fields, GitHub/private repository content, catalogue data, credentials and unrelated histories have no allowed input edge into this migration's context materialization, count, summary or serializer. Existing user-entered transcript text still requires independent eligibility re-admission; a saved class or hash is not a confidentiality proof. No DLP perfection is claimed.

Processed media is reused only through its exact immutable binding: undeleted conversation/user-entry/request/attachment, class, complete metadata, source/processed hashes and native record identity. Check every referenced object before activation and before dependent viewing. Missing, partial, corrupt, reordered or cross-chat media denies; an attachment ID alone cannot expose an orphan. Retain unreferenced media and its occupancy separately; no automatic quota reclamation is introduced.

Original PDF/image bytes, filesystem paths and temporary native grants have no new durable field. Pages remain local processed display content, not an implicit later upload. A complete native PDF reading requires owner reattachment and fresh native disclosure under ADR-0020. Page previews cannot reconstruct the PDF or prove hidden objects absent. Display page IPC carries bounded metadata, not media base64 or a binary export.

## Bounded storage, display pages and native exact review prerequisites

Proposed parser budgets for review, **not active constants**: at most 256 KiB of encoded JSON per data chunk; at most 128 references and 64 KiB encoded per index node; at most 64 KiB encoded per commit/control record. JSON escaping and encryption overhead are accounted separately from raw text. Split longer entries only at UTF-8 scalar boundaries into ordinal/offset/total/hash-bound fragments; exact reconstruction must preserve every original byte. Bound index fanout/depth and reject cycles/unreachable aliases. No full transcript, long answer or ever-growing manifest is required to fit one renderer message.

Chunking alone cannot fix current whole-domain allocation. A separately reviewed private storage snapshot API must stream health/replay one bounded record at a time, preserve domain-wide malformed/foreign-file denial, and retain only bounded name/hash/length/native-identity metadata. Record/handle ceilings remain necessary even with a 4-GiB byte ceiling. Keep current-user DPAPI/domain binding, private DACLs, local native NTFS checks, ancestor pinning, no reparse/hardlink/ADS/device/UNC aliases and exclusive writer ownership. Cached indexes or renderers cannot waive these checks. No generic production `read(name)`/path IPC is proposed.

Future display paging may use host-issued conversation/revision/root-bound opaque cursors with closed ordinal ranges. Proposed response bounds are 256 KiB encoded and 32 entry fragments; a four-page cache is at most 1 MiB of encoded page payload, **not** a claim about total React/DOM/decoded memory. Bound live overlays and decoder allocations separately. Reject stale/replayed/cross-chat/out-of-range cursors. Do not reuse current `load_conversation`/adoption on every page: that route has attachment/policy side effects. Full entries may span pages, but cannot disappear or change order.

Host-only context materialization and renderer display paging are separate seams. They reference the same committed source identities without returning active context or grants to the renderer. Later complete native review requires a reviewed paged reader over **one immutable exact canonical outbound byte artifact**, bounded current-page allocations, exact ordinal/completeness verification, owner/cancellation/deadline binding and a separate explicit native confirmation. Page progression, renderer booleans and counts never mean consent. Dispatch must consume exactly that artifact/hash, not reserialize changed context. Current whole-text `ReviewDocument` does not implement this seam, and no maximum full-window body/native memory budget is approved here.

## Quota, orphan, crash and uncertain-write rules

All arithmetic for file lengths, sums, fragment offsets, counts, sequence/revisions and conversions is checked. Positive prospective writes must fit the aggregate ceiling; exact capacity/one-over boundaries need fixtures. Existing immutable tombstones, failed/partial objects and unreferenced orphans are retained and counted, not deleted or treated as free capacity. Strict health corruption remains a denial, not merely a warning from which writes proceed.

Transaction admission must account for exact prepared ciphertext lengths plus all required final commit/control objects. A manifest's quota counter alone cannot reserve disk or establish native reality. Concurrent writers, insufficient free space, unexpected length changes or an uncertain prior append deny. Root must review a single-writer, whole-transaction reservation/retained-terminal-capacity design before production: advisory `has_capacity()` is not a reservation. New user work and summary inference cannot start on the assumption that terminal/recovery publication will find space later. No new reservation can reset or refund independent financial state.

Before the final commit, a crash can leave inert chunks/index/plans. After a valid visible commit, checked replay may activate that **same** commit only if every referenced object verifies; it must not create a duplicate commit. A committed-but-unacknowledged append error poisons cached state until checked replay. No automatic append/provider retry, repaired sequence, deleted partial object, resumed grant or spend refund follows. Preserve uncertain outcomes for attention. Native `sync_all`, identity checks and exact readback remain relevant but do not by themselves prove directory durability, multi-domain atomicity or physical power-loss behaviour.

At capacity, retain read-only access to healthy saved data and give a bounded honest warning for denied new writes. Exact warning copy, pre-reserved terminal/recovery handling and any future explicit owner-controlled export/archive/capacity change require their own reviewed UI/storage contracts. Automatic removal or silent early summary remains prohibited. Original old/media occupancy can consume disk independently of the new quota.
