## 1. Closed intents and immutable native plans

Add only explicit preparation, native-review/apply, cancellation and read-only mutation-status commands. All authenticate the fixed main window. The model, generated package, imported plugin and remote repository text cannot call an apply/confirm route or issue an approval. The renderer can request a native review, never supply `approved`, `confirmed`, an endpoint, HTTP method/header, credential target, serialized grant or approval receipt.

`prepare_github_change` accepts a `deny_unknown_fields` operation-tagged intent. Its variants are `create_branch`, `create_file`, `update_file`, `create_issue`, `comment_issue`, `close_issue`, `create_pull_request` and `merge_pull_request`, with only that variant's bounded fields. Account/installation/repository identities are captured from the host's currently authenticated selected repository, not taken as caller authority. Supplied expected SHAs/IDs/revisions are assertions which must match independent current reads; they do not substitute for those reads. Duplicate JSON fields, inappropriate nulls, wrong types, unknown variants, overflowing IDs, invalid refs/paths, malformed Unicode and over-limit content deny before networking.

Preparation freshly reads the current selected installation/repository and relevant resource state, then constructs one immutable, native-owned plan. Its display DTO is serializable but cannot be deserialized into authority. Bind:

- Contract/policy version, host-generated opaque plan ID, current account ID/login and connection generation, fixed App ID, installation ID, repository ID/owner/name and privacy flag.
- Operation and complete exact payload bytes, native-computed SHA-256, every expected resource ID/revision/content hash, branch/head/base SHAs where applicable, and the captured gate-policy identifier.
- Host monotonic issue time, expiry at most 120 seconds later, one review/dispatch use and the exact maximum remote mutation count of **one**.

Plan IDs are generated by the host; at most one pending plan and one in-flight GitHub operation exist. Any new plan replaces/burns an unused earlier plan. A review/apply request takes the plan by ID from the host, burns it even if denied/cancelled/stale, and accepts no replacement payload. The existing offline `ProposalDescription`/`consume_once` scaffold is not a native dispatch permit and must not be presented as one. The new production dispatch permit is private, move-only and cannot be constructed from any renderer-supplied description or boolean eligibility value.

The native review document binds the entire exact payload and readable old/new content, not merely a digest or truncated diff. Display account, installed repository, target branch/resource, expected revisions, destination, operation, commit title/message or full issue/PR text, notifications/consequences and the applicable guard limitations. Use the existing owned native review with cancellation as default. A denied, expired or incomplete review cannot dispatch.

## 3. Exactly one remote change per confirmation

Every row below is a separate immutable plan and separate exact native confirmation. Creating a branch, changing its file and opening a PR are three changes, not one approval silently reused. Compound automatic rollback/delete and any unreviewed follow-up mutation are absent.

| Operation | Fixed REST mutation / mutation and evidence permissions | Required expectations and supported server guard |
| --- | --- | --- |
| Create branch | `POST /repos/{owner}/{repo}/git/refs`; Contents write | Exact source branch/head commit SHA, host-validated `refs/heads/<new-name>`, target absent. Request contains the captured SHA; it creates, never updates/replaces a ref. |
| Create file | `PUT /repos/{owner}/{repo}/contents/{path}`; Contents write | Explicit named non-default branch/head, file absent, exact UTF-8 content and commit message. No caller author/committer or implicit default branch. |
| Update file | Same Contents PUT; Contents write | Explicit named non-default branch/head, exact existing blob SHA and old/new content. Request includes the existing blob SHA, the documented file-replacement guard. |
| Create issue | `POST /repos/{owner}/{repo}/issues`; Issues write | Exact title/body, issues enabled; no labels, assignees, milestones, projects or arbitrary fields. |
| Comment issue | `POST /repos/{owner}/{repo}/issues/{number}/comments`; Issues write | Stable issue ID/number, current snapshot, exact appended body; reject the `pull_request` discriminator so this intent cannot target a PR accidentally. |
| Close issue | `PATCH /repos/{owner}/{repo}/issues/{number}`; Issues write | Stable issue ID/number, matching open-state/snapshot; send only `state: closed` and the explicitly reviewed fixed state reason. No editing/deleting the issue body. |
| Create PR | `POST /repos/{owner}/{repo}/pulls`; Pull requests write plus Contents read/write for branch evidence | Same selected repository for head/base, two explicit distinct branches with exact head/base SHAs; exact title/body and explicit draft flag. No fork, issue-to-PR conversion, auto-merge or branch update. |
| Merge PR | `PUT /repos/{owner}/{repo}/pulls/{number}/merge`; Contents write plus Pull requests read/write for PR-review evidence | Stable PR ID/number, exact head/base refs/SHAs, reviewed method/title/message and section 5 evidence. Request always includes `sha` for the PR head. |

The endpoint/permission mapping above was checked against primary [Git references](https://docs.github.com/en/rest/git/refs#create-a-reference), [Contents](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents), [issues](https://docs.github.com/en/rest/issues/issues), [issue comments](https://docs.github.com/en/rest/issues/comments#create-an-issue-comment) and [pull requests](https://docs.github.com/en/rest/pulls/pulls) documentation on 10 October 2026. Paths/methods/payload serializers remain host-owned and named; this table does not authorise a generic endpoint adapter.

File content is bounded UTF-8 without NUL/control surprises, at most 64 KiB. Commit title/message use the existing bounded immutable proposal limits. Issue/PR titles are nonempty, at most 256 scalar values/1,024 UTF-8 bytes; bodies/comments at most 4,000 scalar values/16,000 bytes. Existing issue/PR text needed for exact review is capped at 64 KiB; excess denies instead of truncating. Private text is local/native review data and is never automatically forwarded to Meta, generation, compaction or Personalization. Plain-text rendering never executes Markdown links, HTML or instructions.

File writes accept only exact named non-default branches which are independently observed as unprotected, with an empty active rules list. Deny `.git`, `.github/workflows`, credential-sensitive paths, traversal, encoded-separator aliases, ADS, symlinks, gitlinks/submodules and executable-mode entries. Before replacing a file, resolve its actual Git-tree mode/type at the captured branch head: Contents GET may dereference a symlink and is not sufficient mode proof. Accept regular blob mode `100644` only. For creation, check the path and all parent components against the captured tree; no directory/symlink/submodule replacement. New feature refs use a restricted `aster/<validated-name>` namespace, never default/protected refs or tags. No force update, ref deletion, protected-branch change, workflow editing, secret, administration, repository creation/deletion or check rerun route exists.

## 4. Actual guard semantics and unavoidable races

Do not claim universal compare-and-swap or transactional rollback. GitHub's documented Contents update `sha` protects the existing target **blob**, not an atomic expected branch head. The Git ref `force=false` mechanism preserves fast-forward semantics but supplies no expected-old-head parameter; this slice does not expose ref updating at all. Creating a new ref from a captured source SHA does not lock the source branch. If that source changes between final read and creation, the created branch still starts at the exact reviewed captured commit.

The documented issue/comment/create-PR REST mutations do not provide an expected-revision argument. Their immutable snapshot comparisons are host preconditions, not a promised server CAS or an assumed `If-Match` contract. Another actor can change an issue or branch between the last read and dispatch. The minimal issue closure changes only state, and a comment appends only the reviewed text; it cannot overwrite an unreviewed body. PR creation may race head/base movement; post-verification must detect any mismatch and report attention required, not silently edit/close the new PR. Any strict atomic-revision requirement beyond these guarantees leaves that capability inactive until a separately reviewed API contract can provide it.

For a Contents response, retain the returned commit SHA and retrieve the file/tree at that **commit**, checking exact blob/content and the expected branch/repository; do not confuse a subsequent unrelated branch advancement with failure of the known file commit. If the actual commit's parent/head relationship differs from the reviewed head, record the observed effect and attention required. No automatic reset/delete/retry is permitted. A later whole-branch CAS design could evaluate GitHub's fixed `createCommitOnBranch(expectedHeadOid)` [GraphQL contract](https://docs.github.com/en/graphql/reference/commits#createcommitonbranchinput), but would require an explicit ADR/transport/schema amendment; it is not silently added to this REST-only slice.

## 5. Narrow ordinary PR integration

This first REST slice can merge only a same-repository, non-draft, open, non-stacked PR into an independently verified **unprotected** base branch. A fresh authenticated [branch read](https://docs.github.com/en/rest/branches/branches#get-a-branch) with exact branch name/head SHA and `protected=false`, plus a complete empty [active branch-rules list](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch), supplies narrow unprotected-branch evidence. Treat this combination as an evidence-based inference, not an atomic guarantee that administrators cannot change protection after the read. An absent/ambiguous protection field, active rule of any type, protected branch, unknown stack/queue state or inaccessible rules denies this initial capability.

Do not treat a 403/404 from legacy protection as proof that protection is absent. The [legacy protection endpoint](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection) requires Administration read; the registered App has no Administration access. Supporting protected branches requires a later reviewed evidence contract and, if necessary, a separate owner permission decision. This slice changes no App settings or permission ceiling. In particular, Aster's protected real repository remains ineligible for runtime merging through this narrow slice; its development PR integration remains separately unauthorised in this chat.

After exact native review, refresh the PR (stable ID, selected-repository head/base IDs, refs/SHAs, open/not draft), base/head branches, active rules, current reviews, and complete current check/status collections at the **exact PR head SHA**. Unknown mergeability, unresolved changes-requested reviews or stale/inconsistent review evidence denies. For this unprotected-only slice, no required approval rule is inferred from a count of `APPROVED` rows. Do not count an obsolete/dismissed review or infer Code Owner coverage; any gate requiring that analysis is unsupported and denies.

Observe [check runs](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference) and their current suites without filtering out pending/failing states, and [commit statuses](https://docs.github.com/en/rest/commits/statuses#get-the-combined-status-for-a-specific-reference). Each applicable current check/suite must be completed/success, and every latest status context must be success. Neutral, skipped, cancelled, stale, timed-out, action-required, pending, malformed or duplicate/ambiguous current results deny. Fully paginate and verify counts/IDs/App identities; an old successful check cannot override a current queued suite or newer run attempt. Empty collections are reported as **no results**, never invented PASS. The aggregate commit status is documented as pending when no statuses exist: accept that as the distinct `NoStatuses` observation only when complete `total_count=0` and empty results are proved, not when any actual context is pending. No-checks/no-statuses integration is eligible only for a reviewed host policy requiring no project checks and a genuinely unprotected, empty-rule base; the native dialog must state this explicitly.

Host-owned project policy is not taken from repository prose or imported plugins. For `comzulca/Aster-desktop`, it always requires the five fixed successful jobs `source-policy`, `frontend`, `codec-source-fixtures`, `windows-host`, `engineering-installer` from one current exact-head run/attempt, even when GitHub branch rules would require fewer. Verify actual workflow/run/head and merge-ref identity and the current [attempt's jobs](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt); previous-head runs, mixed attempts or missing stronger receipts cannot qualify. The stronger installer gate additionally requires its reviewed bounded receipt proving exactly 15 codec plus 6 resource PASS, causal CPU proof and `qualificationComplete=false`. Until that receipt contract and retrieval are implemented, deny rather than treating the job name alone as complete evidence. This project policy cannot override the protected-branch exclusion above. Add read-permission parsing for Checks, Commit statuses and Actions to the existing installation parser; insufficient permissions deny. Never request write permissions for these evidence channels.

Immediately before dispatch re-read the PR and base/head evidence once more and compare every captured identity/revision; if protection/rules/check/review evidence was changed or became unknown, deny and require a new proposal. The synchronous merge endpoint's `sha` guards **head only**, not expected base. Base, rules, reviews and checks can still move in the last remote gap. State that residual explicitly; no expected-base field or universal atomicity is invented. Dispatch only the reviewed ordinary method, head SHA and exact message. Never call `/merge-async`, enqueue, enable auto-merge, follow a stacked downchain, send a bypass option, weaken a gate or retry an uncertain merge. GitHub's primary PR documentation distinguishes synchronous ordinary merge from asynchronous/queue/stacked operations; those broader operations are outside this one-change grant.

`HTTP 200` alone is not proof. Require a validated `merged=true` response and nonempty merge commit SHA, then independent PR/commit readback matching repository/PR identity and reviewed head/method. For an ordinary merge commit verify the actual head and base parents; mismatched reviewed base or unknown readback is attention required. Squash/rebase need method-specific proof of actual incorporation, not an invented two-parent test; keep those methods inactive until their bounded evidence verifier is separately implemented. A 202/pending/queued/false result is not successful integration. This draft's smallest qualified implementation may therefore expose only ordinary `merge` and explicitly mark squash/rebase unavailable.

## 6. Separate durable dispatch/uncertainty ledger

Before starting **any** mutation request, append and verify a durable immutable dispatch-intent record in a new fixed current-user encrypted `github-mutations-v1` domain. This is separate from credential custody, local catalogue/profile, conversation history and the financial ledger. No financial reservation/refund/reconciliation behaviour changes. Proposed bounds: 16 KiB per record, 4 MiB aggregate and 512 records. Reserve capacity for dispatch plus a terminal record before admitting a plan. No automatic clearing, overwrite, corrupt-store repair or receipt reuse.

Record schema/version, monotonically increasing ledger sequence, host operation ID, plan/payload/review hashes, account/install/repository IDs, operation and bounded expected resource metadata, dispatch time, and later bounded verified resource/commit IDs and outcome. Store no token, raw network error, personal profile, issue/file body, approval capability or replayable HTTP payload. Records use fixed host-generated names. This metadata can itself be sensitive and remains encrypted/local; it is not telemetry or provider context.

Supported terminal observations are `verified`, `rejected_no_change`, `cancelled_before_dispatch`, and `attention_required`. Only a provably unstarted request or documented definitive no-change rejection can be classified unsent/no change. Once networking may have started, timeout, connection loss, cancellation, malformed response, missing readback, epoch change, unwind or failed terminal append is uncertain. Keep the durable intent and show attention required; never automatically repeat, compensate, delete a partial resource or assert rollback. On restart, unmatched dispatch intents restore **uncertainty only**, never tokens, selected account/repository, plans, native approvals or active requests.

Use move-only permit consumption, single-flight state and ledger intent before the fixed adapter request. After a possible write, permit only bounded read-only reconciliation of the exact affected resource; no implicit second mutation. Create/comment outcomes with no returned stable ID may be impossible to identify uniquely from hashes/timestamps, so ambiguous readback remains unresolved. Do not fabricate an idempotency-key guarantee or clear uncertainty just because no match was found. While an account/repository has unresolved intent, further mutations there deny; explicit future human reconciliation needs its own before-code contract. A terminal response DTO reports the exact verified/denied/uncertain state and bounded IDs, not arbitrary content/URLs or secrets.
