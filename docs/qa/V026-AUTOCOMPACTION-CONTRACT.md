The conversation send route uses the fixed Meta Chat Completions endpoint. The host's `History::begin_request_with_attachments` admission rejects further continuation at 20 eligible completed turns or when appending the prompt would exceed 512 KiB of display text. ## Permanent release requirement

Preserve the owner's full-window and initial encrypted 4-GiB retention decisions in [SPEC-0006](../specs/SPEC-0006.md) and [the storage contract](V024-FULL-WINDOW-TRANSCRIPT-CONTRACT-20261010.md). Automatically *plan* a compaction only when the exact active model representation approaches a measured threshold that leaves answer and summary capacity. Do not use 20 turns, 512 KiB, elapsed time, or bytes divided by a constant as a token trigger. Keep complete local history, recent eligible turns and attachment bindings; compact only the context sent to the model. Compaction is not a vault lookup, storage deletion, disk reclamation, or an ability to resurrect invalidated eligibility.

A summary generation, the ordinary request and provider counting each have distinct disclosure semantics. Do not send any of them automatically without their applicable native review. The count request itself contains context; the count is not spending evidence. Summary inference needs its own quota/reservation, settlement and unchanged Contributor rules. Exclude personal/confidential material, private repositories, vault notes, Personalization and credentials. A summary is untrusted model text, not system/developer instructions, moderation evidence or tool authority. Denial, refusal, cancellation, stale context, lost or uncertain output, or lack of headroom must preserve the prior active context and full transcript. Do not silently truncate, overwrite, resend, or reset spending.

## Preventive threshold (FR-030 / SEC-030,036 / TM-033,038 / AC-077 / T-087)

Before code, this slice specifies a deterministic, versioned host planning transition. There is no arbitrary percentage or fixed early token threshold. The fixture takes a supplied, request-bound protective margin for future growth, validates the actual ordinary request plus reserved output, and chooses ordinary continuation only while remaining capacity is strictly above the margin. At the margin it automatically schedules preparation of a summary; it does not dispatch one. If the ordinary no longer fits, the summary can still proceed to review only if its independently counted representation and own output reserve fit. A missing or stale margin is not proof of headroom. A margin at or beyond the whole window is invalid.

The summarization input must be an exact prefix of the admitted prior turn pairs and must leave at least one recent complete turn intact in this fixture. Summary review uses a separate exact count and cannot reuse an ordinary receipt, a different conversation, or a different context/key revision. A simulated plan is private and does not admit disclosure, budget, disk mutation or a live request. Preparing it must not alter full display history. A real activation also needs a measured or otherwise validated conservative upper bound for the next admitted input and summary overhead, followed by exact re-counting after the summary; no portable fixture can establish that provider guarantee. The versioned policy and permanent acceptance tests must not enable silent early fallback.

T-087 synthetic checks: one token above, at and below the protective margin; missing, forged, stale or invalid margin; a full/oversized ordinary request with a valid independent summary; summary oversize; and attempted substitution of receipt, purpose, conversation, revision or key generation. Native disclosure, budget, durable activation and synthetic live provider acceptance remain separate gates.

## Serialized summary and answer recovery (FR-030 / SEC-030,036 / AC-077 / T-087)

Baseline for this slice: merged main `850b81612590b187f9e772a223155cee7898f71b`. The live Tauri send restores saved pairs into SessionState and reserves the new turn before invoking provider serialization. Session restore, reservation, history append, provider body construction and final validation each retain legacy limits. Before runtime promotion, a normal host send and restart must cross both 20 completed turns and 512 KiB before any compaction, send with a verified below-threshold Responses count, then exercise a near-window summary and exact post-summary recount. None of those runtime gates is changed here.

The existing ledger permits one pending reservation and does not permit request-ID reuse. A separate summary operation must use a different request ID from the eventual answer. After restart, use the ledger and durable context evidence, never a renderer assertion or a transport error, to distinguish whether dispatch may have occurred. A dispatched reservation with missing usage is unresolved. Do not redispatch the summary or start answer admission while it is unresolved. Reconciliation or settlement alone does not reconstruct missing, partial or stale output. A terminal fixture candidate is bound to the exact summary body, original revision and output digest. Only a settled candidate, independent counts of the proposed next context and a current revision may reach a separate commit check. This fixture cannot activate a summary. Even observing a verified commit only allows a fresh answer review, not an answer reservation or dispatch.

The fixture classifies evidence states and models restart decisions; it does not implement ledger changes, storage, atomic commit, native approval, payment or the live provider. A production workflow needs a durable dispatch intent before network egress, bounded encrypted staged output with crash recovery, authenticated receipts, compare-and-commit and a separate ordinary answer approval. The counter is context-fit evidence on the same protocol, not financial usage evidence. Do not require equality to billed tokens or presume a free count.

If the answer ID already appears in the authoritative ledger, recovery defers to that existing answer rather than making a new review for it. In the fixture this observation is supplied with the validated checkpoint; a production implementation must obtain it from the ledger, not persist it as a checkpoint flag.

## Rebuild after compaction and prove a second cycle (FR-030 / SEC-030,036 / TM-033,038 / AC-077 / T-087)

After a valid summary of the exact older eligible prefix, construct a prospective context at the next revision with the prior eligible prefix replaced by a bounded, inert assistant text item. No text in that item can become developer instructions, a tool action, or a new user turn. Preserve the exact recent suffix and pending user text. A follow-on summary must carry forward the already compacted context as data and have its own exact count. No old count, guessed savings, or ordinary request can authorize the summary path. For this text-only fixture, use at least two retained turns when evaluating immediate readiness for a possible second summary. Actual contributor classification, provenance, source invalidation and acceptance of this exact input form are separate requirements.

T-087: pass both inherited limits with synthetic saved history while allowing ordinary admission below the supplied threshold; fire precisely at threshold; reject a changed pending input/suffix, a stale or still-too-large rebuilt count, and a second summary that drops or substitutes the first. The fixture never overwrites the full display history. It has no actual provider, consent, ledger or store connection.
