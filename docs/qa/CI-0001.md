Check both lockfiles into source before running CI. The pipeline fails if they
are missing or drift; it does not generate and silently accept new resolutions.
No local observation substitutes for the Windows job. A Windows Server 2025 CI run does not prove native UI,
Windows 11 behavior, interactive Credential Manager entry, guarded file writes,
live provider use, installer signature, or a production release. Each requires
its separately recorded acceptance procedure and exact source/build identity.

If Cargo.lock cannot be generated in the local development environment, run
the **manual** `Generate Cargo lockfile for review` workflow on a reviewed
source revision. It resolves the manifest using the pinned Rust 1.97.0
toolchain, verifies Cargo metadata and uploads `src-tauri/Cargo.lock` together
with the checkout SHA. Inspect the lockfile and its hash, then commit that
exact reviewed file to source. It has read-only repository permission and
does not automatically commit or start live calls. The regular CI job remains
blocked until the lockfile is committed and rerun against the new SHA.

If pnpm cannot reach the registry from the development environment, run the
**manual** `Generate pnpm lockfile for review` workflow on a reviewed source
revision. It uses Node 24 and the exact pnpm 11 version declared by the
project, resolves with `--lockfile-only --ignore-scripts`, and uploads a
candidate `pnpm-lock.yaml` with that source SHA. Review its package versions,
resolved locations and hash before committing it. The workflow has no write
permission, does not run dependency lifecycle scripts, and never autopushes.
After committing either candidate, normal CI must run with frozen/locked
inputs on the **new** source SHA; a bootstrap run is not a passing build.

The read-only **Generate Rust formatting patch for review** workflow runs
`cargo fmt` with the pinned Rust formatter and uploads `rustfmt.patch` alongside
its checked-out SHA. Review and apply that patch to the matching local revision,
then commit it. Formatting on an untrusted later revision or passing the
bootstrap run does not satisfy the normal CI `cargo fmt --check` gate.

CI deliberately has **no NVIDIA credential or provider canary**. Only fixed
provider fixtures belong in source tests. GitHub workflow permission is
`contents: read`; checkout does not persist the ephemeral GitHub token. The
workflow never uses `pull_request_target` or a privileged deployment event.
Official GitHub actions are pinned to full commit SHAs; review Dependabot
updates to those pins before merging. RustSec audit installation is pinned to
an exact published crate version with `--locked`, but fetches the current
advisory database; advisories and registry availability can change between
runs. The committed source dependencies themselves must remain locked.

The local secret guard is heuristic. It inspects tracked UTF-8 text for common
NVIDIA, GitHub, and private key forms without printing a matched value. It is
not a guarantee against encoded, novel, or binary secret formats. Enable and
review GitHub's organization/repository secret scanning separately if the
account plan exposes it. A license inventory lists declared package licenses;
legal suitability remains a human review and is **NOT RUN** until recorded.

`scripts/windows/bootstrap.ps1` is a user-run Windows checkout helper. It
checks Git and Git Credential Manager, refuses an existing destination and
reparse points in the path, and clones over HTTPS to
`$env:USERPROFILE\Documents\comzulca\aster-desktop` after interactive
authentication. Git Credential Manager's GitHub authentication on the user's
Windows session is separate from this conversation's GitHub connector. The
script has **NOT RUN** on the laptop and neither clones nor installs the app
from this Linux environment. Do not disable Windows or ESET protections.

## Recording actual evidence

For each run, record UTC timestamp, workflow run URL, checked-out Git SHA,
runner image and tool versions, all four job conclusions, artifact SHA-256,
all failures and rerun reason under `docs/qa/`. Attach the raw reports through
the private workflow artifacts. A failed check remains FAIL until a new run on
the corrected revision passes; do not relabel earlier failures or substitute
an artifact from another revision. Update the `docs/aster-builder/contract.json`
gate only after its referenced implementation tests have actually passed.
