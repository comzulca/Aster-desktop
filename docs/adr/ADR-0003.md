## Read and proposal boundary

The user selects one root through a native host dialog. Pin the volume serial number and FileId of root and relevant parent chain. Accept only validated relative paths; never trust the renderer or model to supply a root or OS path. Reject every reparse component (including junction/symlink), hardlink count >1, alternate data streams, device/UNC aliases, `..`, `.git`, credential/secret filenames, binary data and oversized content. Read bounded UTF-8 with host-side identity checks. Review Windows filesystem case-folding and reserved-name behavior on the actual target.

The model can produce only a typed, size-bounded proposed edit. The host computes and binds a complete, immutable diff including root and file identity, old/new SHA-256, conversation/request, exact operation, nonce, expiry and use count=1. Present the **whole proposed operation and diff in a native host-owned review window**, where the user confirms or rejects it. A renderer `approved=true`, chat message, model tool call, hidden page or AGENTS.md cannot approve. Consume confirmation once and revalidate identities, content, policy and path immediately before mutation. Any mismatch creates a new proposal after fresh review; do not silently overwrite or auto-approve.

## New-file gate

For a previously absent target, revalidate parent/root identity, use Windows `CREATE_NEW` behavior to avoid overwriting an intervening file, write bounded content, flush, verify identity and SHA-256 and record a durable intent/outcome. Interrupted, inaccessible or ambiguous creation enters `ATTENTION_REQUIRED` and blocks dependent writes until reviewed. Protocol 2 wires this narrower capability through host-owned native review and a private DPAPI journal in the verified engineering build. Exact-source T-040 automatic/process-restart fixtures and final CI/package qualification pass. Owner category acceptance does not supply detailed positive installed proposal receipts or physical power-loss proof; those remain transferred under V02-008/V02-010, with no production promotion.

## Existing-file gate

`ReplaceFileW` is a pathname-based replacement without expected-old-hash compare-and-swap; a last-moment hash check alone is insufficient to claim conflict safety against another process. A candidate native approach is to journal a private recoverable original and intended hash first, open root/parent and target handles under restrictive Windows sharing, verify file IDs and old SHA-256 while the target handle is held, then write through that target handle, flush, verify SHA-256, mark journal complete and clean up. The journal/backup holds restricted project content: store it under the user's protected local app-data area with restrictive access and encryption, bound to the target identity and policy revision. Never silently restore over a different file generation. A crash during in-place writing may temporarily expose partial file contents; recovery must quarantine the target as `ATTENTION_REQUIRED` and require user review before any restore or further mutation. This method cannot promise crash-atomic public visibility or safety against privileged filesystem interference.

The approach is **a candidate, not a proven write feature**. Enable replacement only after tests in a real Windows 11 NTFS environment demonstrate one-use approvals, malicious reparse/hardlink/ADS/path aliases, cooperating and competing writers, delete/rename attempts, identity drift, every journal/write/flush crash point, recovery verification and cancellation before/after mutation. If any required property cannot be achieved, preserve proposal-only behavior and report the failed or NOT RUN gate. Avoid source claims of universal atomicity. A normal POSIX rename test does not validate this Windows path.

## Decision on tradeoffs

The requested MVP includes the ability to apply changes after a separate approval per operation, so this feature remains a tracked requirement. It does not justify a premature mutable-file capability or an assertion of conflict-free writes. The host owns sensitive choices and journals; the UI exposes only capabilities backed by actual evidence. No shell, arbitrary path tool, web or MCP is added to make edits easier.
