# ADR-0004 — Engineering-only capability proofs and credential interoperability

Date: 2026-09-30 UTC. Status: accepted for an implementation candidate, not target-OS acceptance. Related: FR-006–FR-009, FR-011, UX-002, SEC-001, SEC-004–SEC-007; TM-001, TM-004–TM-007, TM-010, TM-012. Extends ADR-0003 without weakening its activation gates.

The original authority excluded certificate creation, trust-store changes, Windows security changes, guest accounts and new accounts. On 2026-09-30 the owner reported **personally enabling Windows Developer Mode** and asked work to continue. Manual Windows 11 acceptance will use the owner's existing administrator account, with normal non-elevated application launch. The owner authorized at most two minimal NVIDIA requests, one per registered model, and will enter the key in Windows Credential Manager. Authorization is not execution evidence.

The owner-reported Developer Mode change does not rewrite that failure as PASS, prove symlink availability under the current token, or pass any NTFS/capability gate. No agent enabled Developer Mode, and no further protection changes are inferred from the request to continue.

## Credential representation

Keep one fixed Generic Credential target and never enumerate/export credentials or expose credential bytes over IPC. Generic blobs are application-defined bytes. Read legacy printable ASCII/UTF-8 and bounded UTF-16LE printable ASCII password representations. Reject malformed, odd-length, embedded/terminal NUL, non-ASCII, whitespace and oversized representations. The decoded key remains 8–256 bytes. Zeroize copied blobs and decoded key buffers; errors contain fixed classifications only. New writes use bounded UTF-16LE without a terminator as the chosen native-password compatibility representation. A disposable synthetic target test exercises both representations. Microsoft does not specify the Control Panel UI's Generic Credential encoding; actual Windows Credential Manager GUI entry/edit interoperability remains NOT RUN until a synthetic owner-entered fixture passes on Windows 11. Reference: https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw .

## Independent workspace candidates

The shipping capability flags and closed IPC permission map stay disabled until independent Windows 11 gates pass. Candidate internals may compile and run synthetic fixture tests, but a successful hosted Windows Server test does not enable a tool. Do not add a renderer approval Boolean, arbitrary tool name, path root or write endpoint.

1. Parse exactly one version-1 bounded JSON proposal object, with an enumerated operation, validated relative path, optional old digest only for new files and bounded UTF-8 new content. Reject unknown fields, approvals, URLs/tools, multiple operations, surrounding prose and stale hashes. A parser output is data, never a grant. Existing-file proposals still require the host's selected/read snapshot and exact identity/hash checks.
2. Build a host-owned review document containing the full untruncated selected content or lossless exact old/new change, target, request/conversation, digest, operation and fixed destination. A trusted native window displays inert read-only text, not HTML or a WebView. A review-document size/encoding failure must deny, never truncate. Closing/Escape denies; no synthetic affirmative click is acceptance evidence. Native consent is kept inside the host, not returned as a replayable renderer token.
3. For a future disclosure path, review the **exact serialized outbound request**, including any prior conversation material. A project-bearing request must not enter continuation history; both file bytes and any answer derived from them must require fresh consent before redisclosure. No network integration or disclosure flag is enabled in this candidate.
4. New-file publication is a Windows-only internal proof seam: pin and revalidate root/ancestor/parent identities, consume one exact native grant, persist a user-scoped encrypted immutable intent before touching the target, use `CREATE_NEW` with restrictive sharing, record the created identity, flush and verify bytes through the same handle, then persist the outcome. Reject concurrent creators; never overwrite/delete/restore on failure. Interrupted intent without provable created identity or any mismatch remains `ATTENTION_REQUIRED`, not success. Journal storage, privacy, ACL, interruption and recovery require their own tests before activation.
5. Existing-file replacement remains unavailable/proposal-only. This change does not implement hash-check-plus-rename or claim exclusive compare-and-swap or crash-atomic visibility.
6. Tighten candidate revocation across operation types: preparing a replacement or creation revokes every previous pending candidate for that conversation, including the other operation type. Maintain one pending candidate per conversation and a combined global ceiling of four. Regression fixtures must deny old IDs/native approvals after either cross-operation transition. This does not activate any shipping proposal or apply endpoint.
