# ADR-0004 — Engineering-only capability proofs and credential interoperability

Date: 2026-09-30 UTC. Status: accepted for an implementation candidate, not target-OS acceptance. Related: FR-006–FR-009, FR-011, UX-002, SEC-001, SEC-004–SEC-007; TM-001, TM-004–TM-007, TM-010, TM-012. Extends ADR-0003 without weakening its activation gates.

## Release decision and owner constraints

The owner selected an **unsigned engineering build**, not a signed/public production release. Preserve the existing `--no-sign` pipeline and `NotSigned` check. The original authority excluded certificate creation, trust-store changes, Windows security changes, guest accounts and new accounts. On 2026-09-30 the owner reported **personally enabling Windows Developer Mode** and asked work to continue. Record this as an explicit owner-made baseline exception, **not an agent modification or authority for further configuration changes**. All remaining Windows/ESET protections must stay unchanged; no additional security, trust-store, elevation or account changes are authorized. Manual Windows 11 acceptance will use the owner's existing administrator account, with normal non-elevated application launch. The owner authorized at most two minimal NVIDIA requests, one per registered model, and will enter the key in Windows Credential Manager. Authorization is not execution evidence.

The prior non-elevated symlink fixture **FAIL with Windows error 1314** remains historical evidence. A later source-bound rerun recorded in `LOCAL-0002.md` passed its exact fixture after the owner-reported Developer Mode change, without rewriting the earlier failure. Neither result proves symlink availability for the current changed source, normal installed-app token or all NTFS/capability gates. No agent enabled Developer Mode, and no further protection changes are inferred from the request to continue.

## Credential representation

Keep one fixed Generic Credential target and never enumerate/export credentials or expose credential bytes over IPC. Generic blobs are application-defined bytes. Read legacy printable ASCII/UTF-8 and bounded UTF-16LE printable ASCII password representations. Reject malformed, odd-length, embedded/terminal NUL, non-ASCII, whitespace and oversized representations. The decoded key remains 8–256 bytes. Zeroize copied blobs and decoded key buffers; errors contain fixed classifications only. New writes use bounded UTF-16LE without a terminator as the chosen native-password compatibility representation. A disposable synthetic target test exercises both representations. Microsoft does not specify the Control Panel UI's Generic Credential encoding; actual Windows Credential Manager GUI entry/edit interoperability remains NOT RUN until a synthetic owner-entered fixture passes on Windows 11. Reference: https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw .

## Independent workspace candidates

Protocol 2 reports four host-owned capability Booleans. `projectRead`, `proposals` and `applyNewFile` describe the wired engineering candidate; `applyExistingFile` is hard false. A capability bit is not acceptance evidence, and an incompatible or unknown status shape denies. Candidate internals may compile and run synthetic fixture tests, but a successful hosted Windows Server test does not certify the installed tool. Do not add a renderer approval Boolean, arbitrary tool name, path root or generic write endpoint.

1. Parse exactly one version-1 bounded JSON proposal object, with an enumerated operation, validated relative path and bounded UTF-8 new content. `expectedOldSha256` is mandatory for replacement and forbidden for new-file creation. Reject unknown fields, approvals, URLs/tools, multiple operations, surrounding prose and stale hashes. A parser output is data, never a grant. Existing-file proposals require a fresh second native file choice whose host snapshot path/hash exactly match the parsed values.
2. Build a host-owned review document containing the full untruncated selected content or lossless exact old/new change, target, request/conversation, digest, operation and fixed destination. A trusted native window displays inert read-only text, not HTML or a WebView. A review-document size/encoding failure must deny, never truncate. Closing/Escape denies; no synthetic affirmative click is acceptance evidence. Native consent is kept inside the host, not returned as a replayable renderer token.
3. For project disclosure, serialize the exact outbound provider request first and show those exact bytes in an owner-HWND native review. Reserve a host-only one-use approval, revalidate the selected snapshot and send that byte sequence once without reserialization. A project-bearing request must not enter continuation history; both file bytes and any answer derived from them require fresh consent before redisclosure. Failed/cancelled egress revokes the snapshot; completion retains only the bounded proposal right, and the 60-second heartbeat removes expired five-minute rights/plaintext. The renderer receives metadata only, never selected project plaintext.
4. New-file publication is a Windows-only engineering capability: pin and revalidate root/ancestor/parent identities, consume one exact native grant, persist a user-scoped encrypted immutable intent before touching the target, use `CREATE_NEW` with restrictive sharing, record the created identity, flush and verify bytes through the same handle, then persist the outcome. Reject concurrent creators; never overwrite/delete/restore on failure. Interrupted intent without provable created identity or any mismatch remains `ATTENTION_REQUIRED`, not success. Exact-source journal/process-termination/restart fixtures pass; hosted CI/package evidence remains required before engineering handoff. Every feasible current-principal-laptop observation follows handoff and blocks installed new-file acceptance or production promotion, not the verified unsigned engineering handoff.
5. Existing-file replacement remains unavailable/proposal-only. This change does not implement hash-check-plus-rename or claim exclusive compare-and-swap or crash-atomic visibility.
6. Tighten candidate revocation across operation types: preparing a replacement or creation revokes every previous pending candidate for that conversation, including the other operation type. Maintain one pending candidate per conversation and a combined global ceiling of four. Regression fixtures must deny old IDs/native approvals after either cross-operation transition. This rule does not by itself activate broader authority: ADR-0009 governs the current shipping `proposals` and new-file `applyNewFile` paths, while existing-file apply remains hard false.
