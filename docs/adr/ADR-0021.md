# ADR-0021 — v0.2.4 pre-implementation custody and capability decisions

Status: proposed implementation contract, 9 October 2026. Source baseline main `d8b9422eab83526a67bd16a23fbb0d029870d709`. These decisions enable design/code work, not untested live capabilities. [Specification](../specs/SPEC-0006.md), [threats](../security/THREAT-MODEL-0006.md).

Current applicability: the dated 10 October amendments below extend the earlier offline-only slice into controlled partial implementation. They do not turn this decision record into an acceptance or delivery receipt.

## Decisions

10 October before-code extension: the [startup measurement contract](../qa/V024-STARTUP-MEASUREMENT-CONTRACT-20261010.md) preserves the current presentation timers and mitigations and adds only bounded native timing observations with critical slots. A shorter minimum is a separately reviewed experimental candidate, never a consequence of a single clean recording or early renderer readiness. The owner personally performs the repeated tests; no agent app/setup launch or merge authority follows.

1. Preserve the separate v0.2.3 source/delivery. Develop v0.2.4 in its own checkout. Existing frozen evidence, financial state, processed media and migration IDs are not overwritten. The latest owner UI reference overrides Aster_builder's default JPG; visual changes do not enlarge caption/window/clipboard authority.
2. Add a host-owned key-authentication state, separate from syntactic key presence and the terms/budget/transport states. A fixed model retrieval verifies current-generation authentication without inference. Success does not promise quota/payment. Native secret custody, caller authentication and no repeated background verification remain mandatory. Invalid/unavailable/deleted/replaced proof cannot start a new conversation; history display remains local.
3. Implement GitHub as a **built-in reviewed host REST broker**, not an arbitrary imported MCP process. Use a dedicated owner-registered GitHub App and device flow with its public Client ID; no embedded secret/private key/backend or reuse of Codex tokens. Separate `github.com` device/token routes from `api.github.com` closed resource routes; disable redirects and prevent credential forwarding. Existing `reqwest`, `serde`, `serde_json`, `tokio`, `zeroize` and Windows credential APIs provide the implementation foundation; dependency review may conclude that no new runtime package is necessary.
4. Device authorisation is an explicit bounded session: fixed verification URL, provider interval respected, slow-down handled by increasing the minimum wait, expiry/cancellation final, and no unsolicited code acceptance. A polling transition is not a general retry licence. Token refresh is a separate single-owner rotation with protected transactional publication; unknown outcomes require reconnect, not replay. Account identity and installed/selected repository scope must be verified before enabling use.
5. GitHub mutations, including PR integration, require separate native exact confirmations bound to current account generation, stable repository ID, operation/resource, expected revision and content hash, expiry and one use. The model may propose, never confirm or commit. Local disable/disconnect/switch invalidates pending work before credential changes; late callbacks remain stale. Local token deletion is not remote GitHub revocation; offer a fixed trusted settings link and explicit wording for that distinction.
6. Import/edit/generate portable skills/plugins as bounded inert packages. Instructions have no host privileges. The built-in GitHub connector is not replaceable by package-supplied executable paths or endpoints. General third-party script/MCP execution is deferred under the latest owner instruction. No script runtime, dependency resolver, hook or package-manager invocation is added to run Aster_builder.
7. Store Personalization in a new versioned current-user encrypted local domain with the exact field/aggregate bounds. Do not attach custom instructions/nickname/occupation/details to ANY provider prompt, compaction input, generated package, tool payload or diagnostic. Profile data can affect local display only; any future provider-facing profile requires a new service/data contract and authority. Clear removes the active Aster copy, not backups or forensic remnants.
8. Context compaction is an explicit host protocol/storage project. First qualify the actual request's admission accounting and safe new history/context bounds. OpenAI `responses/compact` and opaque items are not assumed interoperable. Meta currently documents client-managed compaction; any additional summary inference consumes a separate admitted budget and carries no grants. Do not silently switch to Responses or raise limits before reviewed fixtures/migration tests. No compaction capability is enabled by this ADR alone.
9. Rendering work starts with lifecycle-owned read-only observations, then a cause-specific minimal patch. Keep the current dark-background and one-shot reveal invariants until evidence supports a separately reviewed change. No longer sleep, repeated hide/show, force repaint, GPU/environment/security exception or speculative WebView upgrade is a claimed solution.

### 10 October full-model-window owner decision

The owner rejects early compaction at the inherited 20-turn/512-KiB limit and requires the full Muse Spark context window. SPEC-0006 revision 5 records that resolved requirement. This requires a reviewed bounded protocol/context-store migration and exact count/output-reserve contract; simply raising constants or using a Responses count for a differently templated Chat request is not qualification. Stateless Responses is a design candidate only, with provider-held history, private profile/GitHub inputs and automatic restoration of original PDFs or grants excluded. Current transport/storage/admission limits remain unchanged until that implementation is reviewed and tested. This decision grants no live request, budget reset, hidden disclosure or new active endpoint.

### 10 October transcript quota preference and observation refinement

The owner chooses 4 GiB initially for new encrypted display/context history, separately from processed attachments, with no automatic deletion/trimming and warn/deny on new writes at capacity. This resolves the initial value, not the still-proposed aggregate ciphertext metric, native streaming/replay, shared transaction accounting or lossless migration. The [transcript contract draft](../qa/V024-FULL-WINDOW-TRANSCRIPT-CONTRACT-20261010.md) preserves legacy bytes and commit-last independent display/context revisions; root implementation approval remains pending. No model-token-to-byte assumption, current limit increase or active compacting route follows.

The [visibility-origin observation refinement](../qa/V024-WEBVIEW2-OBSERVATION-CONTRACT-20261010.md#before-code-saturated-event-buffer-visibility-refinement) preserves a native origin and event together within the existing 96/60,000-ms budget, not a cure or readiness change. The [dated provider-document review](../qa/V024-META-COUNT-DOCUMENTATION-20261010.md) records contradictory injected-token statements; exact count and financial integration remain separately reviewed prerequisites. No free endpoint or guessed overhead is assumed.

The owner expressly asserts the necessary rights and permits redistribution of the supplied Aster Builder inert instructions/resources, excluding the PowerShell installer and executable scripts. The owner will install/run the later Windows diagnostic themselves. The agent still does not launch app/setup or change security/GPU settings. Longer initial delay remains excluded as cure evidence. Mechanical version/expected-installer identification follows the **before-code** integration-contract amendment: source manifests become `0.2.4`, with five CI jobs, fifteen codec/six resource probes and all budgets/provenance checks unchanged. General app release/signing/merge authority is absent. The partial source status, failed compile and unfinished operations are tracked in the [current checkpoint](../qa/V024-IMPLEMENTATION-CHECKPOINT-20261010.md), not inherited from v0.2.3.

An official remote GitHub MCP server would add transport/schema/auth/permission/remote-content boundaries without being necessary for the current closed connector. A local Node/Python MCP server adds unrequested execution and sandbox qualification. Both remain out of this slice. Device flow avoids a distributed secret but has phishing risk; the trusted popup must display account/app/source clearly and direct the owner only to the fixed GitHub verification page. GitHub rights do not override Contributor data restrictions. A later registered App, successful CI or connected account cannot retroactively qualify changed package bytes or fix the owner-observed native flash.
