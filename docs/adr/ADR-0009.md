## Decision

Use protocol 2 between the React renderer and Rust host. The status response contains exactly four Boolean workspace capabilities: `projectRead`, `proposals`, `applyNewFile`, and `applyExistingFile`. The first three may be true only on the Windows engineering implementation that supplies their closed commands; `applyExistingFile` is hard false for v0.1.0. The renderer rejects an incompatible protocol/capability shape, and neither model output nor renderer state may change the host registry.

The native folder picker establishes the root. A separate native file picker issues a one-use grant and creates a bounded host snapshot. The renderer receives only relative path, request ID, SHA-256 and byte count; project plaintext never crosses IPC. When the user sends that file, the host composes a project-bearing prompt bounded to 32 KiB (deny, never truncate), reserves the request as ephemeral, serializes the exact selected NVIDIA request body, and presents the full exact body in a native review window owned by the authenticated main WebView HWND. Denial or close sends zero bytes. Approval is a non-serializable, move-only host value bound to the review digest. The host consumes it once, revalidates root/file identity and hash, and gives the already reviewed bytes directly to the fixed provider transport without rebuilding them. Failed/cancelled egress revokes the snapshot; completion retains only its bounded proposal right. Grants expire after five minutes and a host heartbeat removes expired plaintext/candidates every 60 seconds. The project-bearing prompt and its derived answer are not inserted into later continuation history.

The model may return only one closed version-1 proposal object. Unknown fields, prose, multiple operations, approvals, URLs, tool names and invalid bounds deny. The same owner-HWND native surface reviews the complete inert proposal. For `create_new`, one approval may call the guarded Windows publication path: revalidate pinned root/parent and target absence, persist bounded current-user DPAPI metadata in a creation-time private-DACL journal, use `CREATE_NEW`, flush and verify through the same handle, then persist the terminal outcome. Recovery is conservative and ambiguous state becomes `ATTENTION_REQUIRED`; no blind delete, restore or cleanup is authorized. For `replace_existing`, the host requires a second native file choice, reads a fresh host snapshot, and admits the proposal only when its relative path and expected old SHA-256 exactly match that choice. Confirmation then yields `proposal_only`, consumes/revokes the candidate and never mutates the file.

## Rejected alternatives

- Sending project text through renderer IPC or trusting a renderer attachment object would make the WebView a data/authority boundary and is rejected.
- Reviewing a summary and reserializing the provider body later would not bind consent to transmitted bytes and is rejected.
- Returning an approval token to JavaScript, accepting `approved=true`, or letting the model select a tool/path is rejected.
- Enabling existing-file replacement through hash-check-plus-rename or `ReplaceFileW` without a demonstrated Windows conflict/recovery primitive is rejected.
