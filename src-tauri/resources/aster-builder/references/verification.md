# Evidence and promotion gates
For each phase, record status PASS, FAIL or NOT RUN. A PASS requires real commands or exact manual steps, timestamp UTC, environment, source revision, result and evidence path; include artifact SHA-256 for artifact-bound claims. A FAIL is retained, never overwritten by a speculative PASS. A NOT RUN names the reason and blocked capability. Re-run gates after changes that invalidate their evidence. Source CI, a packaged unsigned engineering output, a live provider call, a signed installer and deployed web/MCP each require separate evidence.

The optional docs/aster-builder/contract.json ledger is created and checked by scripts/harness_gate.py. Explicit policy.storage_enabled, policy.web_enabled and registry entries determine which optional gates apply. It enforces types, trace IDs and references, closed policy declarations and gate metadata. It does not inspect app runtime code, prove accessibility, confirm live APIs, scan dependencies, validate signatures or confer deployment authority. Do those checks with the target project's actual commands and real OS. Bind the policy and fixtures to a revision so a repeated run is comparable. An evidence ledger committed after the tested source commit may refer to that earlier source SHA; a subsequent behavior change invalidates the corresponding gates.

Forward-test with these independent situations: (1) provider specified but credential design absent; (2) model requests shell or tool privilege expansion; (3) project file changes between proposal and commit; (4) provider endpoint unverified; (5) web/MCP lacking auth, egress or cost gates; (6) CI passes with an unsigned older-revision artifact; (7) retire a provider while preserving historical migrations. Fail validation if the workflow skips specs/threats/acceptance, exposes secrets to UI, lets model content grant authority, invents an outcome or presents a conditional integration as deployed.

Report which requested capabilities are usable, mocked, disabled or unverified. For any release candidate list required/observed gates, source and artifact identity, residual risk and explicit decision. Do not hardcode Aster's budget, roster, toolchain versions or release identifiers into a new application.
